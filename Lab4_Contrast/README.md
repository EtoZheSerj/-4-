# Лабораторная работа 4 — вариант 4

**Изменение контраста относительно среднего значения яркости.**

WinForms-приложение (.NET 10, `net10.0-windows`): асинхронная многопоточная обработка
изображения тайлами, пул фиксированного размера, критические секции, события
синхронизации, отмена и асинхронное сохранение.

## Формула варианта

1. Средняя яркость кадра (по всему изображению):
   `M = Σ(0.299R + 0.587G + 0.114B) / N`
2. Каждый канал каждого пикселя:
   `c' = clamp(M + k·(c − M), 0, 255)`

`k > 1` — контраст растёт, `0 < k < 1` — падает, `k = 1` — изображение не меняется.
Альфа-канал сохраняется. Коэффициент `k` задаётся в интерфейсе.


## Интерфейс

* «Открыть...» — входное изображение (PNG/JPEG/BMP/GIF).
* «Потоков в пуле» — размер пула; он же лимит семафора (одновременных фрагментов).
* «Коэффициент контраста k» — параметр варианта (по умолчанию 1.5).
* «Задержка на фрагмент, мс» — демонстрационная пауза (0 по умолчанию): нужна, чтобы
  успеть нажать «Отмену», потому что кадр 12 Мп обрабатывается ~0,2 с.
* «Запустить обработку» — прогресс в процентах этапов, по завершении в статусе
  «Готово за N мс, M = …».
* «Отмена» — прерывает обработку; результат не собирается и не сохраняется.
* «Сохранить результат...» — асинхронная запись PNG.

## Схема конвейера

```
UI-поток
   │
   ├─1─► асинхронное чтение файла: FileStream(FileOptions.Asynchronous) + ReadAsync
   ├─2─► декодирование в Task.Run → общий буфер BGRA _src (далее только чтение)
   ├─3─► ФАЗА 1: тайлы 64×64 → очередь _sumQueue → пул потоков
   │        WaitAny(_cancel, _jobSignals[i]) → тайл [lock] → WaitOne(_permits)
   │        → сумма 299R+587G+114B → накопление и счётчики [lock] → Release(_permits)
   │        последний тайл: _sumDone.Set()
   ├─4─► оркестратор: WaitAny(_sumDone, _cancel) → M = Σ/(1000·N)
   ├─5─► ФАЗА 2: под lock публикуется M, _stage = 2, тайлы → очередь _applyQueue
   │        пул: c' = M + k·(c − M) в приватном буфере → копия в _dst [lock]
   │        последний тайл: _allDone.Set()
   ├─6─► оркестратор: WaitAny(_allDone, _cancel) → Join всех потоков пула
   └─7─► асинхронный писатель: копия на UI-потоке → PNG в Task.Run → WriteAsync/FlushAsync
```

## Критические секции (`lock (_sync)`)

1. Очереди этапов `_sumQueue` / `_applyQueue` — постановка и изъятие заданий.
2. Накопитель яркости `_brightnessSum`, `_pixelCount` — суммы по фрагментам.
3. Общий буфер результата `_dst` — копирование готового тайла.
4. Счётчики `_passDone`, `_sumCount`, `_applyDone` и флаги `_stage`, `_sumClosed`,
   `_applyClosed`, `_cancelled`, `_meanBrightness`.
5. Вне замка: обработка пикселей в приватном буфере, чтение неизменяемого `_src`,
   отчёты о прогрессе (чтобы UI-колбэк не выполнялся под замком).

## События синхронизации

| Примитив | Роль |
|---|---|
| `AutoResetEvent[] _jobSignals` | «появилось задание» (по одному на поток пула) |
| `ManualResetEvent _sumDone` | барьер между фазами: «средняя яркость посчитана» |
| `ManualResetEvent _allDone` | «все фрагменты обработаны» — можно собирать результат |
| `ManualResetEvent _cancel` | «отмена», видна всем потокам сразу |
| `Semaphore _permits` | не более N одновременно обрабатываемых фрагментов |

Ожидание этапов построено на событиях (`WaitHandle.WaitAny`), а не на `Thread.Sleep`.

## Отмена и завершение

* `Cancel()` выставляет `_cancel` и будит все потоки пула; реакция ~30 мс.
* Поток ожидает семафор порциями по 50 мс и проверяет отмену; после разрешения
  проверяет её ещё раз.
* Отмена учитывается в обеих фазах, при чтении файла и во время демонстрационной
  паузы (она снимается тем же событием, а не `Thread.Sleep`).
* `StopWorkersAsync` выполняет `Join` всех потоков — «зависших» потоков не остаётся.
* При отмене `ProcessAsync` возвращает `null`: результат не собирается, файл не пишется.
* Файлы открываются через `await using` (`FileOptions.Asynchronous`) и закрываются всегда.
* Отчёты о прогрессе ограничены частотой 50 мс (последний — всегда): без этого тысячи
  сообщений забивают очередь UI-потока, кнопки перестают реагировать, а прогон 12 Мп
  растягивался с ~0,2 с до ~18 с.

## Замеры для отчёта

Меняйте «Потоков в пуле» (1, 2, 4, 8, 16), запускайте обработку и берите время из
статуса «Готово за N мс». Пример на кадре 4000×3000 (фрагмент 64×64, k = 1.5, 12 ядер):

| Пул | Время, мс | Ускорение |
|----:|----------:|----------:|
| 1 | 153 | 1.00× |
| 2 | 119 | 1.29× |
| 4 | 97 | 1.58× |
| 8 | 76 | 2.01× |
| 16 | 74 | 2.07× |

Ускорение ниже линейного: декодирование PNG и сборка результата выполняются
последовательно, а на сами преобразования уходит малая доля времени.

## Проверено автотестом

* средняя яркость `M` совпадает с независимым расчётом по всему кадру;
* пиксели результата совпадают с формулой `M + k(c − M)` на всём кадре, `k = 1` не меняет кадр;
* результаты при пулах 1, 4 и 7 идентичны (детерминизм, нет гонок);
* отмена в фазе 1 и в фазе 2: возврат `null`, нет зависших потоков, файл не создан;
* через GUI: отмена во время работы — статус «Отменено пользователем», результата нет;
* сохранение PNG асинхронно, файл читается, идущая отрисовка не конфликтует с записью;
* 8 последовательных прогонов с разными размерами пула — одинаковый результат.
